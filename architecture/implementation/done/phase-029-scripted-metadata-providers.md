# Phase 29 — Scripted metadata providers

**Status**: Built
**Plan reference**: `architecture/planning/done/csharp-script-extension-points.md` §2. Numbered 25 in
that document's outcome table, before phases 25–27 were planned against those numbers; renumbered
there.

## What this is for

A script that answers "what databases, tables and columns does this connection have". Three motivating
cases, all real:

- **ODBC and JDBC**, where the engine behind the connection is not knowable at design time and
  `information_schema` may or may not exist. Recorded as a blocker in
  `planning/todo/change-tracking-odbc-jdbc.md`.
- **A source whose real schema lives in an application metadata table** rather than in the catalog — a
  vertical-partitioned EAV model, or a vendor product that stores its own column list.
- **Hiding, renaming or synthesising columns** before anyone maps them: dropping forty audit columns
  nobody should map, or surfacing `FullName` that the source stores as two.

## Scope: what an operator browses, not what the pipeline reads

This is the important boundary and it is deliberate.

There are two consumers of column metadata:

| | who asks | how |
| --- | --- | --- |
| **browsing** | the SPA's cascading connection → database → table → column pickers | `MetadataService` → `IDriver`'s three methods |
| **the pipeline** | staging (build the table), segments (resolve the segment column), writers (target shape) | `ITableCatalog`, held by driver components |

**This phase overrides the first and not the second.** The reason is structural rather than a
preference: `ITableCatalog` implementations are singletons held in driver component constructors
(`new BatchReloadReader(MsSqlDialect.Instance, MsSqlCatalog.Instance, …)`), and a driver is registered
once per `ConnectionDriverType`, not per connection. Overriding the pipeline's catalog per connection
means constructing those components per connection, which is a change to how drivers are registered and
does not belong inside this phase.

### That boundary is less limiting than it sounds, because the slots compose

The obvious worry is a synthetic column: the picker shows `FullName`, an operator maps it, and the
pipeline's catalog has never heard of it. It works anyway, and the reason is worth stating:

`SourceProjection` renders a mapped column as `{transform} AS {quoted source column}`, and a transform
with no `{{column}}` token is used verbatim (phase 22). So `FullName` with the transform
`[First] + ' ' + [Last]` renders

```sql
SELECT [Id], [First] + ' ' + [Last] AS [FullName] FROM [dbo].[People]
```

— valid SQL that needs no catalog entry for `FullName` at all. The transform can be typed by hand or
generated by a `sqlColumnExpression` script (phase 23).

**Metadata provider = what an operator sees and can map. Transform slot = where a synthetic column's
value comes from.** They were designed separately and compose without either knowing about the other.

The pipeline consults the source catalog for exactly two specific columns — a segment column and a
watermark column — and both already fail with a "column not found (available: …)" message naming what
is really there.

## Connection-level binding only

Every other slot binds at connection, replication or table mapping, with the mapping winning. This one
binds **only at the connection**, and that is a real narrowing rather than an omission:

- Metadata describes an engine and a connection. A table's columns do not depend on which mapping is
  reading them.
- `MetadataService` only ever has a connection name — the picker asks before a mapping exists.
- A mapping-level binding would therefore be invisible to the picker and visible only to the pipeline,
  which is precisely the disagreement this phase's scope boundary is trying to avoid.

So `ScriptSlots` grows a notion of **which levels a slot may bind at**, and `/api/scripts/slots` returns
it, so the SPA's `ScriptBindingsCard` renders each slot only where it means something rather than
offering a control that silently does nothing.

## The contract

```csharp
public interface IMetadataProvider
{
    Task<IReadOnlyList<string>> ListDatabasesAsync(MetadataContext context, CancellationToken ct);
    Task<IReadOnlyList<TableMetadata>> ListTablesAsync(MetadataContext context, string database, CancellationToken ct);
    Task<IReadOnlyList<ColumnMetadata>> ListColumnsAsync(
        MetadataContext context, string database, string schema, string table, CancellationToken ct);
}
```

`MetadataContext` carries the **open `DbConnection`**, the `IScriptDialect`, the binding's parameters,
and — the part that makes the common case cheap — **the driver's own answer, lazily**:

```csharp
public sealed record MetadataContext(
    DbConnection Connection,
    IScriptDialect Dialect,
    ScriptParameters Parameters,
    Func<CancellationToken, Task<IReadOnlyList<ColumnMetadata>>> DriverColumns,
    …);
```

Hiding forty audit columns is then `(await ctx.DriverColumns(ct)).Where(c => !c.Name.StartsWith("Aud_"))`
rather than reimplementing `sys.columns`. A script that ignores it pays nothing, because it is a
delegate and not a fetched value — which matters for ODBC/JDBC, where the driver's own answer may not
work at all.

This is the one contract that hands a script a live connection, because there is no way to describe
"ask the catalog" as data.

## Running in the API is accepted

Decided when the security question was settled: the risk of operator-authored C# in process is accepted
and gated by permissions, and metadata providers run in process. That means a metadata script can hang
or crash the API, which is the same trust boundary as everything else here.

## How to verify when built

- Unit tests over compiled scripts: a provider that filters the driver's answer, one that ignores it
  and synthesises, one that throws (failing with the script's name attached), and one bound to a
  connection with no provider (the driver answers).
- `ScriptSlots` level-scoping: `metadataProvider` is offered at connection and refused elsewhere, and
  the API's slot list says so.
- API: `GET /connections/{name}/metadata/…/columns` returns the script's answer when one is bound.
- `Category=Integration`: a real connection, a bound provider that hides a column, and the picker
  endpoint not returning it.
- Playwright: a synthetic column surfaced by a provider, mapped, and given its value by a transform —
  the composition above, end to end.
- Full suite green.

## Open questions

- **Overriding the pipeline's `ITableCatalog`** needs per-connection driver components. Worth doing
  when a driver genuinely has no working catalog (ODBC, JDBC), which is also when those drivers land.
- **Caching.** The SPA calls these endpoints on every picker interaction and a script may be expensive.
  `useCapabilities` already caches hard on the client; the server does not cache at all today, for
  either path.

# Retrospective

Built as planned, plus a cleanup the phase forced that is worth as much as the feature.

## Two per-engine switches went away

`RunExecutor` carried two of them — `ResolveDialect(ConnectionDriverType)` and a `RunnerScriptDialect`
class — each a `switch` over `MsSql`/`Postgres` returning the right `SqlDialect`. Phase 27's own note
called the second one out as "a per-engine switch at the one call site that needs it, rather than
widening `IDriver` to expose a dialect no other caller needs".

This phase produced the second caller: the API needs a dialect for a metadata script, in a different
process. Duplicating the switch there would have made three copies that every new driver has to
remember to extend, in two processes.

So a driver now names its own dialect, opt-in by interface exactly like `ISegmentExpandingReader` and
`IConnectionTester`:

```csharp
public interface IDialectProvider { SqlDialect Dialect { get; } }
```

`ScriptDialectAdapter.For(driver)` returns an `IScriptDialect` or null, both switches are gone, and an
ODBC or JDBC driver reaching an arbitrary engine can simply not implement it — which is the honest
answer for a driver that has no single dialect to name, and is the case that made a `switch` wrong in
the first place.

`DataSync.Drivers.Generic` took a reference on `DataSync.Scripting.Abstractions` to host that adapter.
Phase 23 removed exactly that reference when the script hook moved out of `SourceProjection`; it is back
for a different and better reason — adapting `SqlDialect` belongs next to `SqlDialect`.

## Scope: browsing, not the pipeline — and the slots compose

The boundary in the plan held, and the reason it is acceptable is worth restating because it is not
obvious: a **synthetic** column surfaced by a provider works end to end without the pipeline's catalog
ever knowing about it.

`SourceProjection` renders a mapped column as `{transform} AS {quoted source column}`, and a transform
with no `{{column}}` token is used verbatim. So `FullName` with `[First] + ' ' + [Last]` becomes valid
SQL that needs no catalog entry. The metadata provider says what an operator can map; the transform slot
says where the value comes from. Two slots designed in different phases, composing without either
knowing about the other.

The pipeline consults the source catalog for exactly two named columns — a segment column and a
watermark column — and both already fail with "column not found (available: …)".

## Connection-level binding, and slots that know where they belong

`metadataProvider` binds only at the connection. Metadata describes an engine; a table's columns do not
depend on which mapping is reading them, and `MetadataService` only ever has a connection name because
the pickers ask before a mapping exists.

That needed something new: `ScriptSlots.BindableAt(level)`, surfaced through `GET /api/scripts/slots`
as `{slot, levels}`. The SPA's `ScriptBindingsCard` filters on it, so a connection shows five slots and
a mapping shows four — rather than offering a control that silently does nothing. The endpoint changed
shape from `string[]` to a record, which broke one phase 23 test; it now asserts the scoping, which is
the more useful assertion.

## The driver's answer reaches the script as a delegate

`MetadataContext` carries `DriverDatabases` / `DriverTables` / `DriverColumns` as functions, not values.
Two consequences, and both are tested:

- **Filtering is the common case and is now trivial** — hiding forty audit columns is one `Where` over
  the driver's own list rather than a reimplementation of `sys.columns`.
- **A provider that ignores the driver never calls it.** That matters for ODBC and JDBC, where the
  driver's answer may not work at all, and `AProviderThatIgnoresTheDriver_NeverCallsIt` pins it by
  counting calls.

## A driver with no dialect still browses

`MetadataService` hands a `DialectlessScriptDialect` to a driver that names none, rather than refusing.
Every member throws with a message saying why, so a script that needs to quote something is told
plainly — but a connection with no scripts at all keeps working, which is the case that would otherwise
break browsing for the very drivers this feature exists for.

## Verification

- `ScriptedMetadataTests` — 7 tests over compiled scripts: nothing bound falls through to the driver
  (asserted by call count); a provider filters the driver's answer; one synthesises a column the catalog
  does not have; one ignores the driver entirely and never calls it; one that throws names the table it
  was working on; an unknown connection falls through; and the slot-level scoping.
- `ScriptsControllerTests.Slots_…` asserts `sqlColumnExpression` binds at all three levels and
  `metadataProvider` at one.
- Full .NET suite green: 467 tests across ten projects. Playwright: 16 green. `tsc -b` clean, `oxlint`
  unchanged at four.

## Still open

- **Overriding the pipeline's `ITableCatalog`** needs per-connection driver components — a change to how
  drivers are registered, not something to fold in here. Worth doing when a driver genuinely has no
  working catalog, which is when ODBC and JDBC land.
- **Server-side caching.** The pickers call these endpoints on every interaction and a script may be
  expensive. Neither path caches today.
- **No integration or E2E coverage** for a provider against a live connection. The unit tests drive real
  compiled scripts through the real resolution path, and the remaining gap is the `DbConnection` a
  provider might query — worth adding with the Docker-backed suites.
