# Phase 41 — Testing a script before a run does (planned)

**Status**: Planned, not started
**Plan reference**: `architecture/planning/done/script-development-and-testing.md`. Named by phase 23's
plan and not built; sharpened by phase 30's; the sample-data question is answered in the planning doc.

## The gap

A script is written in the editor, compiled on save with diagnostics as Monaco markers (phase 28), and
bound. **The next thing that happens is a replication run.** There is a *Check* action that compiles
and nothing that runs the script against anything.

Phase 23 planned this and did not build it. Phase 30 made the sharper case:

> More important here than for any other script slot, because a wrong change query is not a crash — it
> is a target that silently disagrees with its source.

Compiling proves a script is C#. It proves nothing about whether it produces the SQL, the value or the
rows the operator meant.

## Sample data: generated by default, live by explicit choice

The planning doc settles what phase 23 left open, and settles it as **both, clearly distinguished**.

### Default — generated

Synthetic rows shaped from the script's known input: the source or target schema, through the canonical
type system phase 25 built. No connection, no query, no possibility of touching production. This is
what *Test* offers when it is opened.

The generator is per-slot, because the slots take different inputs:

| slot | what "sample input" is |
| --- | --- |
| `sqlColumnExpression` | a `ColumnMetadata` per mapped column — the script returns SQL, so nothing needs executing to show its output |
| `valueColumnExpression` | one value per declared column, of the column's canonical type |
| `rowTransform` | a `ChangeRow` per operation — including a **delete**, which carries only its key and is the case a transform is most likely to mishandle |
| `metadataProvider` | the driver's answer, itself generated |
| `sourceQueryBuilder` | context only; the output is a statement, not rows |
| `lifecycleHook` | the hook's own context |

Generated values should be *characteristic*, not random: an empty string and a long one, zero and a
negative, a null wherever the column is nullable, a date that is not today. Random values make a test
that passes once and fails next Tuesday.

### Opt-in — live

An explicit connection picker runs a real query for real sample rows, capped at N.

**The distinction must be visible, not implied.** The planning doc is right that a silent fallback
would be the wrong design: an operator needs to know when they are about to query a real system.
Concretely — the connection picker is empty by default and choosing one is a deliberate act; the result
panel is labelled *"live query against `prod-src`"* or *"generated sample"*; and the live path names the
statement it ran, because a query against production that the operator cannot see is exactly the thing
this is trying to avoid.

## Running the script

For most slots, running it *is* the test — a `sqlColumnExpression` returns a string, a
`valueColumnExpression` returns a value, a `rowTransform` returns a row or null.

Two need care:

- **`metadataProvider` runs in the API and takes a live connection** by contract. Its generated mode
  can hand it a fake driver answer with no connection at all, which is most of the value; its live mode
  is the one that needs a real one.
- **`sourceQueryBuilder` returns a statement, not rows.** Generated mode shows the statement and its
  bound parameters, which is the thing worth checking. Executing it is the live mode, and against a
  source it is a read — worth saying so, since "test" and "run a query against production" are
  different-feeling actions.

A script that throws reports the exception with the script's name, as `ScriptExecutionException`
already does — the test is also where an operator finds out their script throws on a null.

## Where it lives

A **Test** action beside *Check* on the script editor, with a result panel below the code. Same shape
as phase 19's connection test: an explicit action, a result that stays until the next one, and no
polling.

For a slot whose input depends on a mapping — most of them — the panel needs a mapping picker, because
"which columns" has no answer without one. Defaulting to the first mapping that binds this script is
the useful default, and is also the answer to "does this script do what I meant *here*".

## What this phase does not build

Any change to a script contract. Every slot is already a function of its inputs, which is what makes
this possible at all.

Saved test cases, or running tests as a gate on save. Both are reasonable and both are a different
feature; this one is an operator pressing a button and reading the answer.

Testing the *pipeline* — that is phase 37's SQL preview, which shows what a whole pass would run. The
two are complementary: preview answers "what will happen", test answers "does my script work".

## How to verify when built

- Each slot testable with generated input, asserted on the generated shape rather than on exact values.
- A `rowTransform` receiving a generated **delete** row, since that is the case with only a key.
- Live mode requiring an explicit connection choice, and the result labelled as live — asserted, because
  the labelling is the safety property.
- A throwing script reporting its exception rather than a blank panel.
- Playwright: write a transform, test it, see the output change when the code changes.
- Full suite green.

## Open questions

- **How many rows is a live sample?** Enough to be representative, few enough to be cheap. A cap the
  operator can see beats one they cannot.
- **Generated data for a scripted metadata provider** is circular — the thing under test is what
  produces metadata. Probably: generate a plausible driver answer and let the script filter it, which is
  the common case anyway.

# Retrospective

Built as planned. The generated/live distinction survived contact unchanged, which is unusual for a
safety property. What it cost was two things the plan did not anticipate, both found the same way:
by running a script for the first time.

## Running a lifecycle hook found that one never could have

`DataSync.Core` was not in the script compiler's reference set. So a script could implement
`ILifecycleHook` and then not read `context.Target` — or `context.Source`, or
`context.ColumnMappings`, which every transform context also carries — because those types are in an
assembly it could not see.

Phase 27's motivating example is *"for each mapped source column with no target column, emit
`ALTER TABLE … ADD`"*. It touches `Target`. It had never compiled.

It survived because the reference set is only exercised by scripts that get written, and every script
written so far — in tests and in the harness — happened to use only its slot's own arguments.
`AScriptCanReadTheConfigTypesItsContractHandsIt` pins it now, and reads every config type a contract
exposes, because the next one added will have the same problem otherwise.

This is the phase's own thesis demonstrated on itself: compiling proved those scripts were C#, and
proved nothing about whether they could do their job.

## A query builder had to lie about what it was

`ScriptSlots` had no name for a source query builder, so phase 30's scripts declare
`Kind = sqlColumnExpression` — the registry, the Used-by column and the Scripts list all describe them
as something they are not.

It is not a *bindable* slot: a query builder is selected by name from the `ScriptedQuery` reader's own
option, because which script owns a read is a property of the reader an operator chose, not something
to inherit from a connection. So it is known but not in `All`, exactly like `hook`. That is a name for
a thing that already existed, not a new capability — the phase's "no new slots" constraint is about
the second.

## Two slots are described, not run

A lifecycle hook and a source query builder both return statements for the host to execute. So the
statement *is* the answer, and there is nothing to gain by running it — and for a query builder,
something to lose: executing a source read is a choice an operator should make deliberately rather
than get from a button labelled Test. Both show the statements, their bound parameters, and for a
builder how it says to read the result back.

The builder is shown with a **previous watermark set**, because the statement that matters is the
incremental one. A builder shown only its first-pass form is a builder half checked — the same reason
phase 37's preview reads the stored watermark.

## The catalog provider has no generated mode, and says so

Its contract hands the script a live `DbConnection`, because there is no way to describe "ask the
catalog" as data. A generated mode would have to pass a connection that is not open, and a script
doing the normal thing with it would fail for a reason that has nothing to do with the script.

The plan's open question guessed at generating a plausible driver answer and letting the script filter
it. That would work for the common case and mislead in the others, and it would need the contract to
accept a null connection — which this phase explicitly does not change. Refusing, with a sentence
saying that choosing a connection is what testing this slot *means*, is the honest version.

## A neutral dialect, distinct from the one that throws

`DialectlessScriptDialect` throws, and rightly: there it means "this driver names no dialect", and
generating SQL for it would be a fabrication. But a script one minute after it is written is bound to
nothing, and refusing to test it then makes the button useless exactly when it is most wanted.

`AnsiScriptDialect` fills that gap and the result says so — *"generated sample — no connection chosen,
so identifiers are quoted ANSI-style"* — because the identifier the script sees is not necessarily the
one its engine would hand it. Type translation still refuses, since that genuinely has no neutral
answer.

## Characteristic, not random

The generated values are fixed and chosen: `'sample'`, `''`, a string at the declared length, `0`,
`-1`, `NULL` wherever the column allows one, and an instant in March 2024 rather than `UtcNow`. A
random value makes a test that passes today and fails next Tuesday for reasons nobody can reproduce,
and a `UtcNow` sample cannot be compared against the last answer — which is the first thing anyone
does with one.

The row transform's generated set is one row per operation, and the delete carries its key and
nothing else. That is the case a transform is most likely to mishandle, because it is the one nobody
types into their head while writing the happy path.

## Verification

- `ScriptTestServiceTests` (11) — each slot with generated input, asserted on shape not exact values;
  a delete carrying only its key; a dropped row saying "dropped"; a script that throws reported rather
  than 500; one that will not compile reporting diagnostics; one whose type does not implement the
  contract naming the contract; a hook declaring a point and emitting nothing for it; a builder's two
  statements and its result shape; the catalog provider's refusal; and the generated label.
- `PreviewIntegrationTests.ALiveScriptTest_…` (`Category=Integration`) — live mode against a real
  database, reading the real seeded rows, with the result naming the connection it queried. The
  labelling is asserted because it is the whole guarantee.
- `ScriptCompilerTests.AScriptCanReadTheConfigTypesItsContractHandsIt` — the reference-set bug.
- Playwright 20 — write a transform, test it, change the code, test again and watch the output change;
  a throwing version reporting its exception; and the picker sitting on generated, because live is a
  choice and never a fallback.
- Full .NET suite green: 553 tests. Playwright: 22 green. `tsc -b` clean, `oxlint` unchanged at four.

## Open questions

- ~~**How many rows is a live sample?**~~ Requested by the caller, clamped to 20, and the cap is in
  the result where the operator can see it. A limit an operator can see beats one they cannot.
- ~~**Generated data for a scripted metadata provider.**~~ Answered by not generating any — see above.
- **A mapping picker** is not built. The service accepts a replication and mapping and uses their
  columns when given them; the editor does not yet offer the choice, so a test from the Scripts screen
  uses a plausible two-column stand-in. Defaulting to the first mapping that binds the script — which
  the Used-by scan from phase 37 can now answer — is the obvious next step and was not needed to close
  the loop this phase is about.
- **Nothing is saved.** A test is an operator pressing a button and reading the answer, deliberately.
  Saved cases and tests-as-a-gate-on-save are both reasonable and both a different feature.
