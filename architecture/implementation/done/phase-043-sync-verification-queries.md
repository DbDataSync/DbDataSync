# Phase 43 — Sync verification queries (planned)

**Status**: Planned, not started — **blocked on phase 42** (`phase-042-declarative-parameter-system.md`).
This phase's own parameter needs (column pickers, typed inputs, vararg) are phase 42's first real
consumer; there is no version of this phase that doesn't need phase 42's `ParameterDescriptor` to already
exist.

**Plan reference**: `architecture/planning/done/add-support-for-sync-verification-queries.md`.

## What this is

The ability to run queries on both source and target to validate that data is synchronizing and
consistent — standard built-in checks (row count, row count by group, sum, sum by group), and
operator-authored checks, reusable and parameterized by table.

## A new script slot

A verification check binds like every other script kind — `ScriptResolution`, git-backed storage,
manifest, compile-on-save (`csharp-scripting-host.md`) — not a parallel mechanism. "Reusable... injects
table names automatically" is the existing parameter-binding shape from that host, now richer courtesy of
phase 42.

## Authoring a check: three ways

- **Built-in generators.** Row count, row count by group, sum, sum by group — one generator per driver
  dialect, in the same style as the existing statement builders (`WatermarkStatement`,
  `StagingStatement`, `BatchReloadStatement`, …). Grouping and measure columns are `ColumnPicker` vararg
  parameters (phase 42), resolved against the table mapping so an aliased column (`cust_id` on source,
  `CustomerId` on target) is one selection, not two. Cardinality is a per-parameter `min`/`max`, not a
  fixed "3" — capped only by phase 42's system-wide guardrail.
- **SQL, generic or per-dialect.** A custom SQL check can be written once as **generic** SQL run against
  both sides when the operator judges the engines' SQL close enough, or written **per dialect** (separate
  source-flavored and target-flavored text) when it isn't. A manifest choice, not a forced two-query
  requirement.
- **C# verification query generators.** A new script contract (peer to `sourceQueryBuilder`) that can use
  source-system metadata to *generate* a verification query rather than execute a fixed one. Runs through
  the scripting host like any other script kind, with the same `Text`/`Number`/`Bool`/`Date`/`DateTime`/
  `Dropdown`/`ColumnPicker` parameter types phase 42 defines, each independently markable optional.

For a user-defined query (SQL or C#), the manifest declares which result columns are grouping columns and
which are aggregate/measure columns, so results from the two sides can be matched up and compared without
DataSync having to infer it from column names.

## Execution and storage

- **TaskRunner runs the check**, not the API — consistent with phase 39's single-writer state store: the
  API is the sole owner of shared mutable state, and a verification run is a standalone artifact, not
  state. TaskRunner executes the source and target queries and **writes the parquet result directly** to
  disk — no proxying through the API's state channel.
- **A small result index** (run id, mapping/script, timestamp, path) is reported to state the same way a
  normal run reports its outcome, so the API/UI can list and locate past results without holding the
  parquet payload itself.
- **Storage layout and retention are open** — deliberately, per `run-metrics.md`'s precedent that
  retention is a policy question, not an implementation one. Needs a location decision (beside the state
  store's data directory, git-ignored, is the likely shape) before this phase is implemented, not before
  it's designed further.

## Presentation

- Groupings first, then aggregates, split into source and target columns, with differences highlighted.
- **Diff highlighting uses a configurable threshold**, not "any nonzero value" — the whole premise of the
  feature is that latency-driven drift is not automatically a problem, so the default UI experience can't
  be "everything is red."
- **Each side's query execution timestamp is captured and shown**, so an operator can visually weigh a
  diff against the time gap between the two reads rather than guessing whether it's drift.
- Filters reuse the existing table-mapping source-filter shape rather than a new filter mechanism, so an
  operator narrowing a check to a quiet window uses a pattern they already know.

## Testing

Both authoring paths (SQL and C#) get the phase 41 **Test** treatment: autogenerated sample data by
default (no connection, no risk), an opt-in real connection for live sample data, and the result always
labelled which mode produced it — reusing phase 41's testing infrastructure rather than building a second
one for this slot.

## Permissions

Reuses the scripting security model already settled in `csharp-scripting-host.md`: operator-authored
code/SQL running against live connections is an accepted, permission-gated risk, audited via git, same
trust boundary as every other script kind. No new security model to design.

## What this phase does not build

- The declarative parameter system itself — phase 42, a prerequisite.
- Any change to how replications run; verification is a parallel, on-demand capability, not part of the
  replication pipeline.
- A scheduling/automation layer for verification runs — this is an operator-triggered action, same as
  phase 41's Test action and phase 19's connection test, unless a later need for scheduled verification
  shows up.

## How to verify when built

- A built-in standard check (row count) runs against a real mapping's source and target, producing
  matching parquet output and a result index entry.
- A grouped check with more than 3 grouping columns works, bounded only by phase 42's guardrail — proving
  the fixed cap is really gone.
- A generic SQL check and a per-dialect SQL check both produce correctly matched source/target results.
- A C# verification generator using source metadata compiles, binds, and produces a sensible query.
- Diff highlighting respects a configured threshold — a diff under threshold is not highlighted, one over
  it is.
- Each result shows both sides' query execution timestamps.
- Test mode (generated vs. live) is visibly labelled, per phase 41's precedent, for both SQL and C#
  authoring paths.
- A verification run does not touch the API's state-store write path directly (TaskRunner writes the
  parquet; the API only receives the index record).
- Full suite green.

## Open questions

- Exact parquet storage location and retention policy.
- The system-wide vararg cardinality guardrail's number — owned by phase 42, consumed here.

# Retrospective

Built, and larger than most — a config shape, two statement generators, a comparison, a file format, a
new project, a state table, a third RunKind, an API, a screen, a script contract and a test mode. The
decisions worth recording are the ones about *where things live*, because those are what stop this
becoming a second replication pipeline sitting beside the first.

## A check names its columns once

The single design choice everything else follows from: a check declares its columns by their **target**
names, and each side's statement is derived. That is what makes an aliased column — `cust_id` on one
side, `CustomerId` on the other — one selection rather than two things to keep in step.

It has a consequence that is easy to miss and would have been a silent bug: the source side must render
each column through the mapping's **transform**, not just its name. A mapping that writes
`UPPER(name)` to the target and a check that grouped the source by raw `name` would compare `alice`
against `ALICE` and report a difference that is not one. `SourceProjection.RenderExpression` was
extracted for exactly this.

## A verification run is a run

Same queue, same lock, same logs, same history — a third `RunKind` rather than a parallel mechanism.
A parallel one would have been a second answer to "what is this replication doing", and two answers is
how a console starts disagreeing with itself.

What is different is what it produces, and that goes nowhere near phase 39's state channel. That
channel exists to serialise writes to shared mutable state; a result is a standalone artifact —
possibly large, never updated, read transactionally by nothing. The TaskRunner writes the parquet
straight to disk and reports through the channel only the index record saying where the file is,
as an outcome like any other, journalled like one, and idempotent on `(run, check)` because a replayed
journal applies its outcomes again.

## The threshold is the feature, not a setting on it

"Diff highlighting uses a configurable threshold, not any nonzero value" is in the plan as a UI note.
It is actually the premise: a replication is behind by design, a check run mid-pass *will* differ, and
a screen that paints that red teaches an operator to ignore red.

So the threshold is a fraction of the larger side — one number that means the same thing for a group of
ten rows and a group of ten million — and a difference under it is **still reported as a number**.
Hiding the small ones would leave an operator unable to tell "equal" from "close", which is the
distinction they are there to make. A measure that was zero is always over the threshold: there is no
proportion of nothing, and treating it as within one would hide rows appearing in a group that had
none.

## Two read times, not one

Kept per side and shown as a gap. A difference is only as meaningful as the distance between the two
reads is small, and without that number an operator is guessing whether they are looking at drift or a
defect — which is precisely what this feature exists to stop them doing.

## The Playwright test found a difference that was already there

It was written to add a row to the target and assert the check noticed. It failed first, because the
two sides *already* differed: test 16 binds a row transform that drops a row, so the source has two
rows where the target has one. The check found it without being told, which is a better demonstration
than a manufactured one — and raising the threshold turns the same finding into a match with the
number still on screen, which is the threshold behaviour the plan asked to see verified.

## Three bugs the screenshots and the tests caught

- **`repeat(0, …)` is invalid CSS.** The result grid's template was built with `repeat(N, …)` and an
  ungrouped check has no grouping columns — which invalidated the whole declaration and silently
  dropped the layout. Visible only in the screenshot, which is what that verification item is for.
- **The results list never refetched.** "Run checks" queues a run; the mutation succeeds the moment
  the work is enqueued and the result arrives seconds later. Invalidating on success refetched too
  early and then never again, leaving an operator staring at an unchanged screen wondering whether the
  button worked. It polls at five seconds now — not the metrics card's thirty, because this is a
  screen somebody is watching immediately after pressing a button.
- **`StateDatabaseTests` caught the new table**, which is what that assertion exists for.

## Parquet.Net 6 is not Parquet.Net 5

No `DataColumn`, `WriteAsync<T>` over `ReadOnlyMemory<T?>` instead, and strings take a dedicated
overload because a string is already a reference type. Found by reflecting over the assembly rather
than by guessing a second time.

## Verification

- `VerificationStatementTests` (9) — both sides derived from one declaration, `GROUP BY` repeating
  expressions rather than referencing aliases (an alias is not in scope there on SQL Server), a
  transformed column grouped by what the transform produces, a column the mapping does not write
  refused, and a filter narrowing both sides the same way.
- `VerificationComparisonTests` (13) — matches, differences as target-minus-source, one-sided groups
  named rather than dropped, either side running out, the threshold as a proportion at two scales, a
  zero baseline always over it, two zeroes equal, multi-measure and multi-column groups.
- `VerificationExecutorTests` (6) — five grouping columns, proving the fixed cap of three is gone;
  generic SQL run on both sides; per-dialect SQL run separately; a script asked once per side; and the
  two refusals.
- `VerificationResultFileTests` (7) — the parquet round trip, both read times surviving separately, a
  one-sided group coming back with no value rather than a zero, an ungrouped check, an empty result,
  multiple measures, and the differing-group count.
- `VerificationResultStoreTests` (5) — the index, and recording the same run and check twice leaving
  one row.
- `PreviewIntegrationTests` (+3, `Category=Integration`) — a check run by a real TaskRunner against
  real databases, grouped by a column the two sides spell differently; a row added to the target that
  nobody replicated, found; and a mapping with no checks refused.
- `ScriptTestServiceTests` (+1) — the generator described rather than run, asked once per side.
- Playwright 24 — the whole loop through the UI, including the threshold turning a real finding into a
  match with the number still shown.
- Full .NET suite green: 630 tests. Playwright: 26 green. `tsc -b` clean, `oxlint` unchanged at four.

## Open questions

- ~~**Parquet storage location.**~~ `<state-dir>/verification/<replication>/<runId>/<check>.parquet` —
  beside the state database, the one directory every process in a deployment already agrees on,
  grouped so a run's results can be found or removed together.
- **Retention** is deliberately not built, on `run-metrics.md`'s precedent: how long to keep results is
  a policy question. The grouping-by-run layout is what a policy will want when there is one, and
  costs nothing meanwhile. Nothing deletes a result today, and the API says so plainly when a file has
  gone missing rather than failing obscurely.
- ~~**The vararg guardrail's number.**~~ Owned by phase 42; 100.
- **There is no editor for checks yet.** They are configured through the API, and the screen runs and
  reads them. A check is a handful of typed fields over phase 42's parameter system, which is why that
  phase came first — but the form is not built, and the Playwright test configures through the API
  and says so.
- **A SQL check gets no Test button.** Phase 41's treatment lands on the *script* path, where there is
  a script to run against generated input. A hand-written SQL check's equivalent is running it, which
  is the Run checks button — worth revisiting if authoring SQL checks turns out to want a dry run
  against sample data first.
