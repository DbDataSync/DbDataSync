# Phase 162 — images embedded, the docs audited, and links rewritten at pack time for the NuGet listing (planned)

Third of three phases split from `architecture/planning/done/embedded-docs-in-the-app.md`. Follows 160K
(the viewer). Independent of 161K.

## Why

Three separate things, grouped because they all change what is *in* the docs and how it reaches a reader:

1. **The images are the one part of the docs that is not offline.** `getting-started.md` has seven
   screenshots at `https://raw.githubusercontent.com/DbDataSync/DbDataSync/main/screenshots/golden-path/…`.
   The embedded copy (160K) has the text offline and a broken picture. And they point at `main`, not the
   version the reader runs.
2. **Absolute URLs are baked into the authored docs and the README.** The root `README.md` links to every
   doc as `https://github.com/DbDataSync/DbDataSync/blob/main/docs/….md` (16 links, plus the seven images in
   `getting-started.md`). They are absolute because the README is packed as the nuget.org listing, where a
   relative path would not resolve — so the authored source is bent around one consumer's limitation. On
   GitHub they work; in the embedded viewer they would leave the app; they always point at `main`.
3. **The docs have not been audited since features landed** — the update commands (phase 158/159), the
   Updates page, `--self-update`, and (160K/161K) the viewer and the Notes setting. Nothing checks the docs
   against the code.

## Design

### One authored form: relative and repo-local

Author the docs and the README with **relative links and relative image paths** — `[Install](docs/install.md)`,
`![…](../screenshots/golden-path/02-connection-form.png)`. GitHub renders these, the repo is browsable
offline, and there is nothing to keep in step by hand. Every absolute consumer is produced from that one
form by a transform at build time; nothing is authored twice.

(The docs already cross-link each other relatively — `](configuration.md)`. The absolute URLs are the
README's doc links and `getting-started.md`'s images. `docs/install.md:135` mentions `github.com` in prose
about trust, which is text, not a link, and stays.)

### Two build-time outputs from that source

| consumer | links | images |
| --- | --- | --- |
| **the embedded docs** (`wwwroot/docs/`) | left relative; 160K's renderer maps `x.md` → `/docs/x` | copied to `wwwroot/docs/images/`, the path rewritten to it |
| **the NuGet README** (`PackageReadmeFile`) | rewritten to `https://github.com/DbDataSync/DbDataSync/blob/<ref>/…` | rewritten to `https://raw.githubusercontent.com/DbDataSync/DbDataSync/<ref>/…` |

- **`<ref>` is the commit SHA, not a tag and not `main`.** `release.yml` creates the tag only *after* the
  package is confirmed published ("the tag becomes a record of what shipped"), so at pack time the tag does
  not exist; a link pinned to it would be dead until later, and `main` is a moving target. The SHA is known
  at pack time and pins the listing to the exact tree that shipped. Local/dev packs, which have no release
  SHA, fall back to the current `HEAD` SHA, and to `main` only if there is no git at all.
- The transform is a small, testable script (or MSBuild inline task) run as a `BeforeTargets` step that
  writes `obj/…/README.nuget.md`, and `PackageReadmeFile` packs *that* rather than the repo-root file. It
  rewrites only what is relative (skips `http(s):`, `mailto:`, `#anchor`) and fails the build on a relative
  link whose target does not exist — the link check falls out of the transform for free.
- Only `raw.githubusercontent.com` image URLs are used because nuget.org restricts README images to a small
  list of trusted domains. I have **not verified** whether nuget.org would resolve a relative link for a
  GitHub-hosted repo on its own; the rewrite removes the dependence on the answer.

### Images embedded

- Only the screenshots the docs actually reference — the seven in `getting-started.md` — ship, not the
  whole `screenshots/` tree (12 MB across 19 folders of test evidence). They are copied into the embedded docs.
- The screenshots are generated by the Playwright suite (`tests/DbDataSync.Web.Tests/screenshots.ts`); they
  are a build artifact of tests, committed. Size is a package concern: measure the seven, and if they are
  large, check whether a lossless optimisation pass is worth it before adding them to every nupkg and every
  snapshot.
- Broken-image behaviour: an image missing from `wwwroot/docs/images/` is a build failure of the transform,
  not a 404 discovered by an operator.

### The audit

Read each of the seven pages against the current code and fix what is stale; add what is missing. Known
starting list: the update commands and the web Updates page and `--self-update` (partly covered in
`install.md` already — check it is complete and correct against phase 159's actual behaviour); the in-app docs
viewer (160K); the `DbDataSync:Notes:RichMarkdown` key (161K, if it has landed); the config reference against
the real `DbDataSync:*` key list.

The audit should leave a check behind, not just a one-off pass: **a drift test** that asserts every
`DbDataSync:*` key the config model defines appears in `docs/configuration.md` (the Admin Config screen
already claims to list "every key docs/configuration.md documents" — nothing enforces that the document and
the code agree).

## What this does not do

- No new documentation *system*: same seven files, same folder, same Markdown.
- No change to the renderer's security posture (160K).
- Does not attempt to regenerate every screenshot; the seven referenced are checked for currency, and if
  the UI has moved on, regenerating them with the existing Playwright script is in scope.
- Does not publish the docs anywhere new (no docs site).

## Checkpoints

1. **Convert the source to relative form** — README doc links, `getting-started.md` images — and confirm
   GitHub renders it (the images resolve from `docs/` to `../screenshots/…`).
2. **The transform**, with unit tests: relative → absolute at a given SHA; `#anchor`, `http(s):`,
   `mailto:` untouched; fragment preserved (`x.md#a`); a missing target is an error.
3. **NuGet README wired in**, and a `package`-job/release-smoke assertion that the packed README contains
   no relative links and its links carry the packed SHA.
4. **Images**: the seven copied and rewritten for the embedded docs; a test that every image reference in
   the shipped docs resolves to a file in the artifact.
5. **The audit** — findings written up in this doc's Progress section (what was wrong, what changed), the
   fixes, and the config drift test.
6. **Verify end to end**: a real `dotnet pack`, read the README out of the nupkg, install the tool, open the
   docs in the viewer with the network disabled and check the pictures show.

## Open questions

- **Image size in the package.** Measure the seven before deciding whether to optimise.
- **Should the embedded docs' images be lazy-loaded / capped** for very wide screenshots? Probably the
  renderer's job (max-width), decided when 160K's viewer is in front of us.
- **Snapshot builds** (158K's `snapshot-*` prereleases): `publish-snapshot.yml` runs the same
  `dotnet pack src/DbDataSync.Cli/DbDataSync.Cli.csproj` as `release.yml`, so a target in the csproj covers
  both, and each is pinned to its own SHA. It builds the SPA as a separate step first (phase 137), so the
  docs copy needs no equivalent — but confirm the snapshot's packed README actually comes out rewritten.
- **`development.md` in the NuGet README's link list** — the README links to it today; nothing here changes
  that, but the listing still sends a package reader to a build-from-source page. Leave, or drop from the
  README's list?
