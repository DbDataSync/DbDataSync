We need to be able to run queries on both the source and the target to validate that data is synchronizing and consistent.

There should be some standard checks, and the ability for a user to build their own scripts per table or as reusable scripts that can inject table names automatically.

For the standard checks, there should be some common ones like total row count, total row count by group (supporting up to 3 columns), as well as total sum of column as well as sum of column by group, also supporting up to 3 groups.  The results should be stored as parquet outside of the definitions repo, but where the user can come back and download them or look at them again.

For a user defined query, the user will need to tell it what columns are aggregate / measure columns so that it can properly combine the results and display them.

When presenting the results, the user should see the groupings followed by the aggregates broken into separate by source and target, with differences highlighted for review.

A difference isn't necessarily considered an issue, since latency between the systems can cause temporary drift.  It will be up to the user to run the queries at good quiet times, or to add filters to reduce noise while still checking consistency.

## Design review (2026-08-28)

Discussed before writing an implementation plan. Confirmed and open items below.

### Binds like a script, is a script slot

A verification check is a new script kind/slot (alongside `rowTransform`, `sourceQueryBuilder`, …),
reusing `ScriptResolution`'s binding, git-backed storage, manifest, and compile-on-save — not a parallel
mechanism. "Reusable... injects table names automatically" is exactly the existing parameter-binding
shape.

### Authoring a check: three ways, not one

- **Built-in generators** — the standard checks (row count, row count by group, sum, sum by group)
  ship as generators, one per driver dialect, in the same style as the existing statement builders
  (`WatermarkStatement`, `StagingStatement`, etc.).
- **SQL, dialect-specific or generic.** A custom SQL check can be written once as **generic** SQL, used
  against both sides when the operator judges the two engines' SQL close enough — or written **per
  dialect** (a source-flavored query and a target-flavored query) when they're not. This is a choice on
  the manifest, not a forced two-query requirement.
- **C# verification query generators** — a new script contract (like `sourceQueryBuilder`) that can use
  source-system metadata to *generate* a good verification query rather than just execute a fixed one.
  Runs through the scripting host like every other script kind.

### Parameters: built on the declarative parameter system (predecessor)

Script parameters today are `{ name, type: string, required }` — not enough for a column picker resolved
against a table mapping, typed inputs, or vararg cardinality (e.g. "up to N" group-by/measure columns
without a hardcoded N). Rather than build that richness narrowly for this slot, it's split out as its own
predecessor: `declarative-parameter-system.md`. Verification queries are that system's first real
consumer — the column-picker-resolves-against-the-mapping requirement (so an aliased column is still one
selection) lives there now, alongside the typed-parameter and vararg-cardinality design.

### Testing, same shape as phase 41

Both authoring paths (SQL and C#) get the phase 41 **Test** treatment: autogenerated sample data by
default, an opt-in real connection for live sample data, and the result always labelled which mode
produced it. Reuse phase 41's testing infrastructure rather than building a second one for this slot.

### Execution and writes: TaskRunner, not the API

A verification run does not go through the API (the single owner of the state store per phase 39). It's
a standalone run, TaskRunner-shaped: TaskRunner executes the source and target queries and **writes the
parquet result directly** — no proxying through the API's single-writer state channel, because parquet
output here is a standalone artifact, not the shared mutable state phase 39's constraint is about. What
still needs a decision at plan-writing time: how the API/UI discovers a run's result (presumably a small
index record — run id, mapping, timestamp, path — reported to state the same way a normal run reports
its outcome) versus the parquet payload itself, which never goes through that channel.

### Confirmed, unchanged from the first pass

- Diff highlighting needs a configurable threshold (not "any nonzero diff"), given the doc's own point
  that drift isn't necessarily a problem.
- Capture each side's query execution timestamp, so a diff can be visually weighed against the time gap
  between the two reads.
- Filters reuse the existing source-filter shape rather than inventing a second filter mechanism.
- Permissions reuse the scripting security model already settled in `csharp-scripting-host.md` — this is
  operator-authored code/SQL against live connections, same trust boundary, same audit trail (git).

### Still open for the implementation plan

- Exact storage layout for the parquet files and the retention question (run-metrics deliberately left
  retention as policy, not implementation — likely the same call here).
- The system-wide vararg upper bound's actual number — now a question for `declarative-parameter-system.md`.
- Depends on `declarative-parameter-system.md` landing first; this doc's script-parameter needs are that
  system's first consumer, not a separate design.
