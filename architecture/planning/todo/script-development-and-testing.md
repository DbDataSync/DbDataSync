# Script development and testing

**Empty as of 2026-08-27 — nothing to plan against yet**, though the title suggests a real gap and one
that has been recorded elsewhere.

What exists today: a script is written in the Scripts editor, compiled on save with diagnostics as
Monaco markers (phase 28), and then bound — and the next thing that happens is a replication run. There
is a **Check** action that compiles, and nothing that *executes* a script against sample input.

Phase 23's own plan named this and it was not built:

> a **Test** action that runs the script against sample input and shows the result. The connection-test
> flow from phase 19 is the precedent — an operator gets to find out it works before a run does.

Phase 30's plan said the same, more sharply, about scripted queries:

> More important here than for any other script slot, because a wrong change query is not a crash — it
> is a target that silently disagrees with its source.

And phase 23 left the open question of **where preview data comes from**: reading N rows from the real
source is the honest sample and is also a real query against production.

## Where preview data comes from (2026-08-28)

Both sources, not one instead of the other:

- **Default: autogenerated preview data/metadata.** Most test scenarios should work out of the box with
  synthetic sample rows shaped from the script's known input (source/target schema, canonical types),
  with no connection required and no risk of hitting production. This is what **Test** should offer by
  default.
- **Opt-in: real sample data.** The operator can also pick an actual configured connection (source or
  target) and run a real query to pull sample rows, for cases where synthetic data doesn't exercise the
  real shape or edge cases well enough. This must be **clearly distinguished in the UI** from the
  autogenerated path — the operator needs to know when they're about to run a real query against a real
  system, not just get a sample. Likely means: an explicit toggle/picker to choose a connection, and a
  visible label on the result ("live query against `<connection>`" vs "generated sample") rather than a
  silent fallback.

This applies to the **Test** action generally — not only scripted change queries (phase 30), but any
script slot with sample input to run against (phase 23's scope too).

**Next step**: this is now specific enough to design as a phase — scope the **Test** action's UI (result
panel, connection picker, autogenerated-vs-live labeling) and the synthetic-data generator's coverage
per script slot (what "shaped from the schema" means for each slot type).
